# 章节课程：从机制到面试推理

面向八年 Java 开发经验，跳过语法和集合入门。章节存在依赖，建议按顺序；已经熟悉的章节也要完成实验与反例。文中 L01～L14 对应 [实验手册](LABS.md)。

基础层必读 [六篇详解](foundations/README.md)。本文件负责串起章节目标和进阶推理；各章的“基础详解”链接承担具体讲解，不再只把基础概念列成待自行搜索的名词。

## 统一的学习与验收方法

每章交付一页笔记：**问题 → 机制图 → 实验预测 → 实际证据 → 改变一个条件 → 结论边界 → 两分钟口述**。先预测再运行，防止看完结果才编解释。

通过标准分三层：能解释当前结果；能预测一个变体；能把机制用于生产故障。死记参数或背出术语只算未完成。每章的源码阅读是深入入口，不要求先学完整套 C++ 才能开始。

## 第 01 章：建立 JVM 与进程的全景模型

**基础详解（必读）：** [F01：执行全景](foundations/01-execution.md)。

**核心问题：一次 Java 方法执行，究竟是谁在工作？**

class 文件是虚拟机指令与元数据的载体，CPU 并不直接执行它。HotSpot 可先解释执行，再将热点方法或循环编译为机器码。Java SE 规定可观察语义，实现可以优化内部表示，只要不破坏语义。因此“规范有操作数栈”与“优化后用寄存器计算”并不冲突。

~~~mermaid
flowchart LR
    Source[Java 源码] --> Class[class 字节码与元数据]
    Class --> Loading[按需加载、链接与初始化]
    Loading --> Interpreter[解释执行]
    Interpreter --> Profile[热点与类型画像]
    Profile --> JIT[JIT 机器码]
    JIT --> CPU[CPU 执行]
    JIT --> Deopt[假设失效时去优化]
    Deopt --> Interpreter
~~~

JVM 是进程的一部分，不是操作系统之外的盒子。堆上限约束不了该进程全部内存；线程、编译器、GC 和 I/O 也竞争 CPU。availableProcessors、最大堆与默认 GC 是环境与 ergonomics 的结果，不是跨平台常数。

**学习要点：** JDK/JVM/HotSpot；规范与实现；解释器、编译器、运行时服务；吞吐、P99、启动时间、内存占用四类目标；测量前记录构建和参数。

**实验：** L01。只改变 Xmx，比较运行时报告；用 jcmd 查看同一进程，而不是从另一条 java -version 猜目标服务配置。

**验收：** 画出源码→class→加载→解释/JIT→CPU 的路径；解释为什么堆 2 GB 的服务 RSS 可以超过 2 GB；区分观测指标与业务目标。

## 第 02 章：class 文件、字节码、栈帧与调用

**基础详解（必读）：** [F01：class、栈帧与逐指令推演](foundations/01-execution.md)。

**核心问题：源码级操作为什么会分解成多步？**

每个执行中的方法有逻辑栈帧，包含局部变量槽、操作数栈和调用所需信息。compute(3,4) 中 iload 把参数压栈，iadd 弹出两个值再压入和，istore 保存到局部槽。字节码的 stack/locals 是解释这个程序的静态约束，并不等于 JIT 后真实机器栈的逐字节布局。

常量池记录符号与常量，运行时解析连接具体类型和成员。普通虚调用可通过类型信息内联，也可能在假设失效时去优化。invokedynamic 是动态链接调用点的机制，不应简单解释成“反射”。

**学习要点：** class 结构、版本、描述符；五种调用指令；异常表；StackMapTable 与验证；类文件常量池、运行时常量池、String.intern 的区别。

**实验：** L02。手动追踪 compute 的栈；比较 synchronized 方法的 ACC_SYNCHRONIZED 与同步块的 monitorenter/monitorexit；找出异常路径为何也释放 monitor。

**验收：** 从 javap 证明 volatile++ 不是单条原子读改写；解释字节码中未出现内存屏障指令，为什么不能推出没有 JMM 保证。

## 第 03 章：类加载、初始化与类身份

**基础详解（必读）：** [F03：类加载、链接、初始化与卸载](foundations/03-class-loading.md)。

**核心问题：同名 class 为什么可能不能互相转换？**

加载得到类型表示；链接包含验证、准备与解析，解析可以延后；初始化执行类的静态初始化逻辑。准备阶段通常提供默认值，不能与执行普通静态赋值混为一谈。编译期常量变量可在使用方内联，因此读取它不必初始化声明类。

类型身份由**二进制名称 + 定义它的加载器**共同决定。父委派是一种加载策略，保护核心类型一致性并减少重复，不是禁止自定义策略的语言定律。发起加载器与定义加载器也要区分。SPI/TCCL 解决父侧框架寻找子侧实现的问题，不等于所有加载都应无条件子优先。

**学习要点：** 主动使用条件；父类与接口初始化区别；初始化锁、初始化失败后的异常；ClassNotFoundException 与 NoClassDefFoundError；类卸载与加载器存活；热部署的缓存、线程与 ThreadLocal 引用链。

**实验：** L03、L04。先预测打印顺序；将编译期常量改为方法返回值；对相同字节分别 defineClass，观察 ClassCastException。

**验收：** 解释为何 Child.value 只初始化字段声明方；解释同名同字节不同类型；为热部署 Metaspace 增长画出保留加载器的根路径。

## 第 04 章：内存区域、对象布局与分配路径

**基础详解（必读）：** [F02：区域、对象与进程内存](foundations/02-memory.md)。

**核心问题：new 出来的对象占多少空间，钱花在哪里？**

先区分规范的运行时区域与 HotSpot 的具体存储。堆承载对象和数组；类元数据主要在本地 Metaspace；机器码在 Code Cache；平台线程有本地栈。虚拟线程的挂起栈可存放于堆中的 stack chunk，不能直接套“每个 Java 线程固定占 Xss”估算。

对象的浅大小包括头、实例字段及对齐填充，不包含它引用的对象。默认传统头与启用紧凑头的布局不同；压缩普通引用与压缩类指针也不是一个开关。默认 G1 下，小对象常走 TLAB 的线程本地指针碰撞快路径；TLAB 仍属于堆，耗尽后还有慢路径和 GC 交互。

**学习要点：** PC、Java 栈、本地调用、堆、方法区；reserved/committed/used/RSS；对象头、数组长度、对齐；TLAB；字符串与包装对象；堆大小与进程预算。

**实验：** L05。比较默认头与紧凑头；比较 Reference 壳和它引用的 1 KiB 数组，明确 shallow size 与 retained size 的区别。

**验收：** 给定字段布局与对齐条件估算大小，再用证据修正；解释“栈里的引用”和“对象在堆上”不冲突；解释为什么不能拿 Xmx 代表容器内存限额。

## 第 05 章：可达性、引用与资源生命周期

**基础详解（必读）：** [F04：根可达性、引用与资源生命周期](foundations/04-reachability.md)。

**核心问题：为什么有循环引用也能回收，有空闲堆却仍可能泄漏？**

追踪式 GC 从根沿引用图寻找存活对象，不依靠每个对象的引用计数。两个互相引用但无法从根到达的对象，仍可回收。相反，被静态集合、存活线程或 JNI 根间接持有的无用对象，GC 无法替业务判断“已经没价值”。

~~~mermaid
flowchart LR
    Root[GC root] --> Cache[静态缓存可达的集合]
    Cache --> Live[业务已不用但仍被保留的对象]
    A[孤立对象 A] --> B[孤立对象 B]
    B --> A
~~~

上图右侧孤立环没有来自 root 的强路径，可以回收；左侧对象即使业务不用，仍然可达。这才是循环引用与保留泄漏的关键区别。

强、软、弱、虚引用表达不同可达性与通知语义。WeakReference 不保证某个时间点清空；软引用也不是容量稳定的缓存方案。PhantomReference.get 始终返回 null，引用队列提供生命周期通知。Cleaner 不是及时释放文件句柄的保证，应优先使用明确关闭与 try-with-resources。

**学习要点：** 常见 GC roots；引用队列；对象死亡与内存回收时机；弱键强值的陷阱；ThreadLocalMap 的弱 key 与强 value；finalization 已弃用待移除，不作为资源管理方案。

**实验：** L06。建立循环，保留弱引用；增加一个静态强引用再运行。先画引用图，再解释输出。

**验收：** 用根路径解释泄漏，而不是仅说“对象太多”；解释不可达不等于立刻释放；解释弱 key 为什么不自动保证 ThreadLocal value 及时释放。

## 第 06 章：GC 共性——分代、屏障与停顿

故障扩展必读：[GC 异常与修复对照](gc-failures/01-allocation-retention.md). 按场景保留日志、提出候选原因，再用 fixed 验证。

**基础详解（必读）：** [F05：算法、分代与跨代引用](foundations/05-gc.md)。

**深入必读：** [G1 的 SATB、跨区入边与疏散](gc/G1.md)，并与 [分代 ZGC 的写侧记录与并发重定位](gc/GENERATIONAL_ZGC.md)对照，分别推演旧值、字段位置和对象地址。

**核心问题：程序边改引用图，GC 如何不漏掉存活对象？**

复制、标记清除、标记整理是基本策略；分代是利用对象寿命分布组织工作，不是规范强制内存结构。只收年轻代时，需要知道老年代指向年轻代的边，不能每次遍历全部老年代。写屏障维护的卡表、记忆集等结构帮助缩小扫描范围，它们不是同义词。

并发标记面对的是不断变化的对象图。以 G1 为例，SATB 通过记录被覆盖的旧引用等机制保留标记开始时快照所需信息，允许浮动垃圾但避免漏标仍需保留的对象。收集器也要处理并发搬迁后的引用访问。这是屏障有成本、低停顿并非免费的原因。

GC 日志中的暂停和应用 P99 不是同一个指标；进入 safepoint 的等待时间也应与停顿内工作分开看。安全点支持某些运行时协调，但“所有安全点都是 GC”不成立。

**实验：** L07。保持存活环约 4 MiB，改变分配量；观察 GC 前后占用。这个实验验证分配压力，不直接证明屏障实现；屏障机制要结合源码与日志解释。

**验收：** 画出 old→young 例子解释记忆集；画一次并发改边解释为什么要屏障；区分分配速率、存活集、晋升与泄漏。

## 第 07 章：G1、分代 ZGC 与选择依据

故障扩展必读：[GC 异常与修复对照](gc-failures/02-g1-pathologies.md). 按场景保留日志、提出候选原因，再用 fixed 验证。

**基础详解（必读）：** [F05：现代收集器及版本边界](foundations/05-gc.md)。

**深入必读：** [G1 完整详解](gc/G1.md)、[分代 ZGC 完整详解](gc/GENERATIONAL_ZGC.md)、[日志实验](gc/EXPERIMENTS.md)和 [24 个专题追问](gc/INTERVIEW.md)。目标包括周期/代际协调、并发正确性、源码入口和压力退化，不能只停在收集器特点比较。

**核心问题：不同收集器把什么工作放到了什么阶段？**

G1 将堆划为 region，年轻代 evacuation 与 mixed collection 都可能有 STW。并发标记判断老年代存活；mixed collection 选择部分老 region 与年轻代一起回收。暂停目标影响启发式选择，是软目标。大于半个 region 的对象走 humongous 路径，分配与碎片问题不能只用“Eden 满了”解释。

JDK 25 的 ZGC 只有分代模式。它通过着色指针、读/写屏障及并发工作降低停顿；仍需要 CPU、内存余量，并可能出现分配等待。不要把旧的非分代 ZGC 文章中的屏障描述原封不动套到分代实现。

Shenandoah 作为对照学习并发搬迁方案；分代模式在 25 产品化但默认仍单代，且不是所有发行版都提供。Serial/Parallel 用于理解小规模或吞吐导向取舍；CMS 只学历史背景。

**实验：** L08。相同堆、相同负载分别运行 G1 与 ZGC，比较阶段与日志，不用短程序运行时间宣布胜负。再单独改变对象大小，观察 G1 humongous 分配。

**验收：** 能说明 G1 各阶段的输入、工作与暂停；能解释 ZGC 低停顿的代价；按 SLO、CPU、内存预算和真实负载提出验证方案，不背“超过某容量必选某 GC”。

## 第 08 章：JIT、逃逸分析、去优化与 AOT

**基础详解（必读）：** [F06：JIT、参数与验证条件](foundations/06-diagnostics.md)。

**核心问题：源码里 new 了，为什么分配计数却接近零？**

HotSpot 通过运行时画像决定编译与优化。内联扩大分析范围；不逃逸且使用方式可分析的对象可能被标量替换，字段变成可独立优化的值，整个分配被消除。这里没有必要先构造一个真实对象再把它挪到机器栈上。

基于接收者类型或分支概率的优化包含假设；类层次或执行路径变化可能触发去优化，恢复到能继续正确执行的状态。OSR 允许长循环中途切到编译代码。Code Cache、编译耗时、预热和反优化都可能影响尾延迟。

JDK 25 的 JEP 514/515 改善 AOT 缓存流程与方法画像复用；训练负载覆盖和运行条件决定效果。不要将其与 GraalVM Native Image 混为一谈。

**实验：** L09。比较不逃逸与发布到静态 volatile 字段的对象分配量，再关闭 DoEscapeAnalysis；结合 PrintCompilation 看编译活动。这个小实验不是 JMH，也不用于吞吐结论。

**验收：** 解释为何“方法很短，所以不会内联失败”不可靠；解释关闭优化前后的分配差异；设计有预热、fork、结果消费和参数控制的正式基准。

## 第 09 章：JMM、发布、锁与竞争

**基础详解（必读）：** [F06：JMM 与运行时区域的区别](foundations/06-diagnostics.md)。

**核心问题：线程看见了标志，为什么能推导数据也可见，却不能保证 ++？**

JMM 描述线程间合法可观察行为，不是 JVM 堆栈区域图。发布线程先写普通字段，再写 volatile 标志；观察方读取相应发布后，利用程序顺序、volatile 同步与传递性建立 happens-before，从而读取到发布前的数据。

volatile 读与写各自有保证，不代表“读→加一→写”这个组合不可分割。锁通过互斥保护复合不变量，并在解锁/后续加锁间建立同步关系。CAS 解决某个比较更新的原子性，但不会自动解决多个字段的事务、ABA 或高竞争重试成本。

**学习要点：** 数据竞争、重排序、as-if-serial；final 字段初始化安全与 this 逃逸；双重检查锁；monitor 的重入、wait/notify 与竞争；锁消除、粗化和实现版本边界；缓存行伪共享与证据。

**实验：** L10。用屏障强制两个线程先读同一 volatile 值再写，稳定制造丢更新；以 AtomicInteger 作对照。不要通过“跑一万次未出错”证明没有数据竞争。

**验收：** 画出 happens-before 链；区分可见性、原子性与有序性；解释 synchronized 的语义与具体锁实现不是同一层次。

## 第 10 章：虚拟线程、调度与 JDK 25 monitor

**基础详解（必读）：** [F06：锁与虚拟线程的面试边界](foundations/06-diagnostics.md)。

**核心问题：一个 carrier 为什么可以承载多个正在等待的虚拟线程？**

虚拟线程可以在支持的阻塞点卸载，把 carrier 让给其他虚拟线程；恢复时不保证回到同一 carrier。它提高大量等待任务的可扩展性，不增加 CPU 核数。CPU 密集型任务仍争用处理器，外部系统容量仍需要信号量、连接池或其他限流。

JEP 491 使持有或等待 monitor 时的虚拟线程能够独立于 carrier 挂载/卸载。它没有取消 synchronized 的互斥语义：同一把锁中的业务仍会串行。JNI/本地代码相关阻塞等剩余 pinning 需要结合 JFR 诊断。

**学习要点：** platform/virtual/carrier 的关系；park 与 sleep；线程转储差异；ThreadLocal 的每线程成本；JDK 25 正式的 ScopedValue 可作为上下文传递延伸，预览 API 不混进必做实验。

**实验：** L11。严格限制为一个 carrier，12 个任务各持独立 monitor，在 monitor 内等待所有任务到达；全部完成说明阻塞任务让出了 carrier，而不是靠扩大线程池补偿。

**验收：** 解释为何相同代码在旧版本可能卡住；为何改成共享锁又保留内部全员等待会构造应用死锁；如何区分锁竞争、pinning 与外部连接池耗尽。

## 第 11 章：OOM、栈溢出与内存预算

故障扩展必读：[GC 异常与修复对照](gc-failures/04-metaspace.md). 按场景保留日志、提出候选原因，再用 fixed 验证。

**基础详解（必读）：** [F06：内存故障分流与参数](foundations/06-diagnostics.md)。

**核心问题：同样叫内存问题，为什么加 Xmx 可能完全无效？**

Java heap space、Direct buffer memory、Metaspace、unable to create native thread 指向不同资源路径。StackOverflowError 是栈深度耗尽，不等于堆耗尽。容器或操作系统杀进程甚至可能来不及由 JVM 抛出 OOM。

进程预算应包含堆、类元数据、Code Cache、平台线程栈、本地库、直接内存及收集器辅助结构，并保留余量。reserved 是地址空间预留，committed 也不能不加区别地当作 RSS。NMT 需要启动时启用，描述 HotSpot 跟踪的本地内存，不能覆盖任意第三方本地库的所有分配。

**实验：** L12、L13。用强引用保留数组耗尽小堆；在堆有余量时耗尽直接内存；改变 Xss 观察递归深度变化。捕获 Error 只为实验输出，不作为生产恢复策略。

**深入作业：** 复用 L04 的字节，反复创建加载器并强引用持有，在小 MaxMetaspaceSize 下观察；再移除保留链。保留链、类数量和卸载日志才是证据，某次 System.gc 没卸载不构成反证。

**验收：** 根据错误消息选择证据，区分容量不足与保留泄漏；解释为何直接内存 OOM 时 heap dump 里可能只有很小的包装对象。

## 第 12 章：生产诊断与综合推理

故障扩展必读：[GC 异常与修复对照](gc-failures/README.md). 按场景保留日志、提出候选原因，再用 fixed 验证。

**基础详解（必读）：** [F06：证据链与综合面试推理](foundations/06-diagnostics.md)。

**核心问题：面对 CPU、P99 或内存报警，怎样用最少假设定位？**

先定义症状、时间窗与影响，再建立候选原因。高 CPU 可能来自业务热点、重试、编译或 GC；P99 升高可能是 safepoint、锁、排队、I/O 或下游。一次线程栈只给瞬时状态，多次采样与时间相关性才能缩小范围。

使用线程转储定位等待关系，JFR 连接 CPU 样本、分配与 monitor 事件，GC 日志解释回收工作，heap dump 回溯强引用路径，NMT 比较本地内存。采样有盲区，heap dump 与某些诊断命令有成本，在线操作应依据影响选择。

**实验：** L14。分别运行 CPU、死锁、保留模式，收集 PID 对应的线程转储、JFR、GC 和 NMT 证据。先写判断再看源码；源码中的故障类型不算定位证据。

**综合验收：** 完成 [五个生产案例](INTERVIEW.md#综合案例)，每题输出“症状→候选原因→证据→排除→改动→同负载回归”。至少能做一次十分钟白板推理，并清楚说明实验不能证明什么。
